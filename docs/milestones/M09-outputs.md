# M09 Outputs, the two audit logs, the review file, printable summary, receipt and saved progress

## Goal

Write the output files, the two audit logs, the printable summary and the receipt, read a signed corrections file back in, and keep saved progress and set-ups on disk in encrypted form. Nothing is written until the operator presses Download, except encrypted saved progress. No file, log or message holds a cell value or the install secret, and only the internal log and the receipt name files. Unmapped columns never leave the tool. A corrected or filled row never says it passed every check. A corrections file is accepted only if it came from this computer's review file and changes only the fields that failed. Resume brings back every decision, matched by file fingerprint and record key. This milestone is engine and session only. The Download, Results and Resume screens come in M12.

### The files (9.1, C-26, C-27, H10)

Each file is CSV, Excel or JSON, chosen per file. The two logs are always text and Data_Quality_Report is always CSV. Everything is built from one `OutputView`, built by `build_view(session)` after `Session.counts()` passed. A file holds mapped fields and the fixed columns below, nothing else.

- OUT-1 (C-26). `OUTPUT_COLUMNS[file]` is the one list. The Download chips and the written header both read it. The operator can switch any column off for Final_Clean_Mapped. Counts never change when one is off.
- OUT-2 (Final_Clean_Mapped). One row per counted row. Columns in order: the canonical fields in the schema, the custom fields, `Count_Status`, `Location_Status`, `Location_Confidence`, `Senate_District`, `Assembly_District`, `Council_District`, then `Latitude` and `Longitude` only when "Exact coordinates, for internal use" is on (P-GEO-6, true point, 6 decimals), then `Source_File`, `Source_Row`, `Record_Key`, `Duplicate_In_File`, `Possible_Duplicate_Of`. Fields hold standardized text, and the original stays in memory and in the review file (H6).
  - `Count_Status` and `Location_Status` use the P-VAL-1 words from the registry. A corrected row says "Counted, corrected from a corrections file". A row filled from its own address says "Filled from the row's own address". Neither can say "passed every check". `Location_Confidence` is High, Low or Not placed. A not-mapped status adds its reason (No fixed address, Outside NYC, Address problem with its problem titles, Not found, No geocoder).
  - `Source_File` is the file name as added, with no folder, plus ` / ` and the sheet name for a workbook sheet. `Source_Row` is the 1-based row as the source program shows it.
  - `Duplicate_In_File` is Yes when the row sits in a copy group or a same-ID group in its table, whatever was decided, otherwise No. `Possible_Duplicate_Of` lists the other members' record keys, sorted and joined with "; ", and is blank when there are none.
- OUT-3 (Unique_Clients). One row per master ID among counted rows, using the high-end grouping (open pairs treated as different people), so the row count equals `Counts.goal1.high`. Columns: `Master_ID`, the mapped name and address fields, `Date_of_Birth` if mapped, `Programs` (confirmed labels, sorted, joined with "; "), `Systems` (display names), `Source_Records`, `Match_Confidence` (M08 `master_match_confidence`, as a registry word).
  - Name, address and date of birth all come from one record, the person's most complete counted record. Most complete means the most non-blank mapped fields, ties by the smallest record key. Fields are never blended from two records.
  - `Source_Records` is `letter :: Source_File :: Source_Row` for every counted record of the person, joined with "; " in table order.
- OUT-4 (Unique_Clients_By_Program). One row per (master ID, confirmed program label), so the count equals `Counts.goal2.high`. Columns: `Master_ID`, `Program`, `Source_Records` (only the records holding that program).
- OUT-5 (Manual_Review_Needed). Every row with an open problem, counted or not (7.3). The layout is in the review-file section below.
- OUT-6 (Set_Aside_Records). Every set-aside row. Columns: `Record_Key`, `Source_File`, `Source_Row`, `Reason` (registry title, such as Summary row or Copy of another row), `Kept_Record_Key` for copies, blank otherwise. A summary row is set aside, so it is listed here and never in the review file (C-11). Clean rows, review rows marked Counted No and set-aside rows together equal rows received, exactly (C-15).
- OUT-7 (Map_Counts). Written on every real run, and never in a practice run (SPEC 9.1, OUT-10). Columns: `Program`, `District_Type`, `District`, `Count`, from M05 `build_map_counts` with `small_cell_max` from `settings/privacy.toml`. A blanked count is written as the registry text "fewer than 11". Entries are one per master ID at the high end. No name, address, ID or point appears.
- OUT-8 (Map_Points). Written only when switched on, off by default. One row per counted, mapped person and program, taken from the person's most complete mapped record holding that program. Columns: `Program`, `Latitude`, `Longitude`, from M05 `build_map_points(entries, mac)`, 6 decimals, in M05's sort order. The offset key is the building's address key (P-GEO-7), so the same building has the same moved point in every file and every run. The receipt and the Excel `Notes` sheet say that a moved point can sit across a district line from its district.
- OUT-9 (Data_Quality_Report.csv). One row per included table. Columns: `Source_File`, `Table`, `Rows_Received`, `Counted`, `Not_Counted_Yet`, `Set_Aside`, `Mapped`, `Counted_Not_Mapped`, one `Problem_<id>` count for each problem ID in `problems.toml` in file order, `Invisible_Characters_Removed`, `Encoding`. No free text (A-03).
- OUT-10 (practice runs, P-GEO-4, fix plan 5.3). When `PlacementResult.practice` is true, every file name starts with `PRACTICE_`, and every CSV, Excel and JSON file gets a first column named `PRACTICE` holding `PRACTICE` in every row, so the first row says it. Both logs open with the line "PRACTICE RUN. Example data, not for reporting." ahead of every other line, and the printable page opens with "Practice run, not for reporting". Map_Counts, Map_Points and the three district columns are not written, because the sample reference gives made-up districts (SPEC 9.1). The receipt says so with the registry sentence `outputs.practice.no_maps`, and Download (M12) shows the same sentence. In a practice run the Download list has seven files.
- OUT-11 (order, C-27). Row tables sort by normalized file name, sheet, then row number, then record key. Person tables sort by Master_ID, then program. The same files give byte-identical outputs whatever order they were added in, except the source letters inside `Source_Records` and the legend, which follow add order (display only, log it).
- OUT-12 (formats). CSV is UTF-8 with a byte order mark and `\r\n`. Excel is written with openpyxl, every cell as text, one sheet `Data`, plus a `Notes` sheet and a header comment where a note applies (exact coordinates, moved points). JSON is a UTF-8 array of objects, keys in column order, every value a string. Text logs are UTF-8 with `\r\n`. A cell that starts with `=`, `+`, `-` or `@` is left unchanged in CSV and stored as text in Excel (a question for Joe).
- OUT-13 (gate and atomic writes). The gate lives in the session layer, because the engine never sees the session (SPEC 3.4, M00's layering test). `session/export.py` has `download(session, folder, settings, clock, confirmed_synced=False, overwrite=False)`. It calls `Session.download_gate()` first, raises `DownloadHeld(reasons)` when held, and otherwise builds the `OutputView` and calls the engine's `write_outputs(view, folder, settings, clock, confirmed_synced, overwrite)`, which takes plain inputs only. It raises `FolderNeedsConfirm(kind)` for a synced or network folder unless confirmed, and `WouldOverwrite(names)` unless `overwrite` is true. It writes each file under a temporary name in the folder, then renames. A failure removes the temporary files. The folder holds exactly the receipt's files afterward.
- OUT-14 (folders, fix plan 2.3). `folder_warning(path, environ)` uses the path and environment variables only (12.5 says a mapped drive cannot be seen). It returns `onedrive` when the path is under the `OneDrive`, `OneDriveCommercial` or `OneDriveConsumer` root, or has a component named `OneDrive` or starting `OneDrive - `. It returns `dropbox`, `google_drive` or `box` when a path component equals `Dropbox`, `Google Drive`, `My Drive`, `Box` or `Box Sync`, ignoring case, and never on a part of a word (`Boxes` is clean). It returns `network` for a path starting `\\`. The callout text is "This folder copies files to other computers. These files hold client data."

### The review file and corrections coming back (8.6, C-06, A-10, fix plan 4.3)

- REVF-1. `run_id(mac, table_keys)` is `"R-"` plus the first 10 hex of `mac(b"run|" + "\x1f".join(sorted(table_keys)).encode())`, over the included tables. `row_signature(mac, run_id, record_key)` is the first 16 hex of `mac(f"{run_id}|{record_key}".encode())`. Known answers with the secret `bytes(range(32))` and table key `clinic_export_csv :: data :: 3380a5d7`. The run ID is `R-aec5efc922`. For record key `7533705e667f8cf12288` the signature is `3848ce28e083e70c`, and the second keyed hash for the shareable log is `fa291d96e4`.
- REVF-2 (layout). Columns in order: `Record_Key`, `Run_ID`, `Signature`, `System`, `Client_ID`, `Source_Letter`, `Source_File`, `Source_Row`, `Counted` (Yes or No), `Reasons` (registry titles joined with "; "), `First_Name`, `Middle_Initial`, `Last_Name` (only on rows whose Client_ID is blank or itself failing, blank on the others), then for each field that fails on some row, `Original_<Field>`, `Standardized_<Field>` and a blank `Corrected_<Field>`. A row fills those three only for fields that failed on that row. Fields that never fail have no columns. No other source column appears (H10).
- REVF-3. `read_corrections(grid, mac, view, file_name, fingerprint) -> CorrectionsRead(accepted, refused, ...)` reads a returned file through M01's reader. Each row is matched by `Record_Key`. It refuses with a code and the line number, never guessing:
  - `not_a_review_file` for the whole file when `Record_Key`, `Run_ID` or `Signature` is missing.
  - `signature_missing` or `signature_wrong` (also another Run_ID or another installation). Both show "This row didn't come from this computer's review file."
  - `originals_changed` when the row's `Original_<Field>` differs from the record's raw value, or `unknown_record` from M08. Both show "This row has changed since the review file was made."
  - `other_column_changed` when a locked cell (identity columns, `Counted`, `Reasons`, `Original_`, `Standardized_`) differs from what the tool wrote, naming the column.
  - `field_not_failing` when `Corrected_<Field>` has text on a row where that field did not fail, naming the field.
  - A row with no `Corrected_` text is skipped without a refusal. A file with no corrections at all says so.
- REVF-4. A passing row becomes a `VerifiedCorrection` and goes to M08's `apply_corrections`, which matches by record key and sets `counted_corrected` when the row now passes. Refusals from both layers come back as one list, each with line, record key where known, code and registry sentence. A refused row changes nothing, and the rest of the file still applies.
- REVF-5 (H8, H9). The corrected text is never logged or saved (M08). The `CORRECTION` audit entry holds the record key, field names, `old_hash`, `new_hash`, the reviewer and the corrections file name (internal log only).

### The two audit logs (9.2, A-02, A-24, C-22, fix plan 4.5)

Both are plain text built only from `AuditEntry` objects (M08), one event per line: `<ISO time, UTC> <EVENT_CODE> key=value ...`. Strings are JSON-quoted. `EVENT_SLOTS[code]` lists the slots each code may carry. Rendering a slot not listed for its code raises. M09 adds a `fingerprint` slot to `AuditEntry` (internal log only) and lists the change in the report.

- AUD-1. `Session.audit_log` is an append-only list of `(time_iso, AuditEntry)`. If M08 did not add it, add it. `History.execute` appends the command's entry. `History.undo` appends an `UNDO` entry naming the decision IDs. Say so in the report.
- AUD-2. Events: `FILE_ADDED` (name, fingerprint), `TABLE_INCLUDED`, `TABLE_EXCLUDED`, `HEADER_CHOSEN`, `SETUP_CHANGE`, `FILL`, `CORRECTION`, `DEFAULT_USED`, `DECISION` (one line per record key, with decision ID and reviewer), `BULK_ACCEPT` (typed count, reason code, both reviewer names), `UNDO`, `AUTO_JOIN` (reason and both master IDs, written once per distinct join), `PAIR_VERDICT`, `PROGRAM`, `RUN` (backend, release, offset applied, kept and lapsed decision counts), `FINISH_REVIEW`, `CONFIDENCE_ACK` (the three measures), `REVIEWER_SET`, `RESUME`, `DOWNLOAD` (file names, internal only). Render every note M03 to M07 emit for fills, defaults and ZIP+4 reduction. Look for them before writing.
- AUD-3 (internal). The first line is "This log contains record keys and file names. Keep it inside the organization." Then a header (product, version, backend, release, whether the offset was applied, table and row counts) and a legend `SOURCE A = <file name>`. It ends with a table of decision counts by reviewer and decision type from `decisions_by_reviewer` (8.7).
- AUD-4 (shareable). The same events, with: source letters only and no legend; no `file_name`, `fingerprint`, `row_number` or `note` slot; a `table_key` shown as letter and table number; each `record_key` replaced by its second keyed hash, the first 10 hex of `mac(b"share|" + record_key.encode())`; reviewer names kept; no reviewer table. Its first line says it has no file names, row numbers or client values, and a claim test proves it.
- AUD-5 (A-24). No cap. A bulk decision on 2,100 rows writes 2,100 lines, and no line says "and N more".
- AUD-6 (A-02, C-22). No line in either log holds a name, street, unit, city, ZIP, date, identifier value or the install secret. The shareable log holds no file name and no Client_ID. Tests scan for both (see Tests).
- AUD-7 (resume). Earlier log lines are not saved (10.1 does not list them). On resume the log starts with `RESUME`, then one `DECISION` line per restored decision with its saved time and reviewer. Say so in the report.

### Saved progress, set-ups and resume (10.1 to 10.3, A-04, A-08, fix plan 5.5)

- STORE-1. Folders are `%LOCALAPPDATA%\Wholecount\sessions\` and `\setups\`. The base directory is injected, so tests use a temporary folder.
- STORE-2. A saved file is `WCS1` plus `dpapi.protect(json_bytes)`. The JSON holds the format version, app version, saved time, the set-up (schema, steps, mappings, defaults, date orders, program columns and groups, run settings, export settings), every `Decision` in `to_json()` form, and per source the file name, normalized name, fingerprint and system. It never holds cell values, rows, corrections text or the install secret. Column names stay because mappings need them.
- STORE-3. `save(session)` runs after each command when saved progress is on (the default). It writes through a temporary name and renames. Switching it off deletes the saved file at once. The switch is kept in `prefs.json` beside the secret, which holds settings only (H9 lists it).
- STORE-4. `purge_expired(base, now, days)` deletes saved progress older than `saved_progress_days` (7) at launch, by file time, because contents need DPAPI.
- STORE-5. `load()` raises `StoreError` with a code for a file from another Windows user, a damaged file, or an unknown format version. Nothing is guessed.
- STORE-6 (set-ups). A set-up is the set-up block without decisions or fingerprints, named by the operator and saved under `setups\`, encrypted the same way. `export_setup(name, path)` writes plain JSON, because DPAPI output cannot move to another computer. The export screen text says it holds column names, steps, mappings, defaults and program names, with no client data. `import_setup(path)` validates the format number, the keys and the value types, refuses unknown keys and files over `setup_max_bytes`, and applies nothing it does not recognize.
- STORE-7 (resume). `resume(saved, added_files)` fingerprints each added file. A saved fingerprint match is `restored`. A match on normalized file name with another fingerprint is `changed`, and the plan names the file. Letters are display only and are not restored. Then decisions replay by record key through M08, and `ResumePlan` reports `restored`, `changed`, `missing`, `extra`, `kept` and `lapsed`, with the lapsed list and reasons (`file_removed`, `record_gone`, `basis_changed`). Rows whose text did not change keep their keys, so their decisions still apply (spec 10.2 wins over fix plan 5.5, which would skip a changed file's decisions). A correction decision lapses with `file_removed` until its file is added again.
- STORE-8 (H9). With saved progress off, the app writes only downloaded files, `key.bin` and `prefs.json`. With it on, also one `sessions\<id>.wcs`. M13 adds only `crosswalk.db` and the calibration folder.

### Errors (A-15, H8)

`safe_error_text(exc)` returns only the exception class name, its module and the line number, never `str(exc)`, the traceback text or locals. `install_excepthook()` shows that text and writes no file. It's the package's only `sys.excepthook`. M14 adds the GUI message box and M10's `error_code` to this same hook rather than installing a second one. The package has no file log handler, and no stream wrapper that writes to disk.
